# 自定义：把一段描述变成风格卡

> 用于自导模式下用户说"我不要这 10 个，我想要……"的时候。
> 这不是第 11 张卡，是**造卡的方法**。产物是一次性的转写表，不写进 `style-index.json`。

---

## 一、先判断：要不要真的新建

**默认答案是"不新建"。** 十张卡覆盖了绝大多数方向；用户描述里的"新风格"十有八九是某张卡 + 一组配色覆盖。

按下面的顺序逐级检查，**命中即停**：

| 级 | 判据 | 处置 |
|---|---|---|
| 1 | 描述只涉及颜色、字体、密度，不涉及结构（圆角体系、边框、阴影方向） | 用最接近的卡 + `decisions.json` 的 token 覆盖。**不新建** |
| 2 | 描述命中某张卡的"最适合"或签名特征 ≥ 2 条 | 用那张卡，把不匹配的一两维改掉。**不新建** |
| 3 | 描述与某张卡的签名特征冲突，但气质一致 | 用那张卡，把冲突的特征写进 `overrides`。**不新建** |
| 4 | 七维里有 ≥ 3 维落在**所有**现有卡区间之外 | 可能是新卡，进入第二节 |
| 5 | 有一个现有卡无法容纳的**结构级**签名特征 | 可能是新卡，进入第二节 |

**关键区分：配色级 vs 结构级。**

- 配色级（不构成新卡）："我想要暖橙色的极简"——极简是结构，暖橙是覆盖。
- 结构级（可能构成新卡）："每个控件都是六边形，所有间距按六边形边长取整"——现有十张卡里没有一张能容纳"非矩形栅格"。

如果只是配色级，**新建卡的代价远大于收益**（见第五节）。

## 二、从自然语言抽七维

拿一段用户原话，按固定顺序抽。**每一维都要写出"从哪句话推出"**；推不出的写 `null` 并说明取规则默认。

| 顺序 | 维度 | 从描述里找什么词 | 抽成什么 |
|---|---|---|---|
| 1 | 中性色温度 | "冷 / 暖 / 纸 / 金属 / 医疗 / 复古 / 米色 / 蓝灰" | `H` 与 `C`，两值都要给 |
| 2 | 彩度上限 | "克制 / 不抢戏 / 活力 / 张扬 / 高饱和 / 莫兰迪" | `C ≤ x`，并给"彩色出现几处" |
| 3 | 圆角区间 | "锐利 / 工业 / 圆润 / 玩具 / 硬边 / 药丸" | 四个值 `sm/md/lg/full` |
| 4 | 边框 | "图纸 / 描边 / 无框 / 分隔线 / 厚重" | 宽度 + 颜色来源 + 用在哪 |
| 5 | 阴影 | "平面 / 漂浮 / 卡片 / 层叠 / 硬阴影 / 无阴影" | 策略 + 三档参数的形态 |
| 6 | 字重区间 | "纤细 / 厚重 / 大字报 / 安静 / 标题党 / 编辑感" | 三个值 `body/strong/display` |
| 7 | 动效强度 | "立刻 / 顺滑 / 有弹性 / 慢 / 高级感" | 时长区间 + 缓动 + 允不允许位移 |

判据与典型误判沿用 `references/translation.md`——那里每个维度都有"方向线索 → 取值"的对照表，**不要在这里重写一份**，直接参照执行。

### 抽取时的三条纪律

1. **一次只读一句话**。用户说"像医疗仪器，但要有温度"，这一句同时给了"青灰底"和"暖"两个冲突信号。处理方式是回问："温度是来自色温，还是来自圆角与留白？"——不要自己折中成 `H 120, C 0.005` 这种谁都不是的灰。
2. **量词优先于形容词**。"卡片圆角大概 20 多""阴影很浅"，量词比形容词可靠。
3. **反例和正例同等重要**。用户说"不要渐变"比"要干净"信息量大得多，它直接进 anti 列表。

### 描述里常见的空洞，必须回问

| 用户可能说 | 为什么不够 | 回问什么 |
|---|---|---|
| "高级感" | 可能指低彩度、可能指留白、可能指短动效 | "是哪一种：颜色收一点、东西少一点，还是动得快一点？" |
| "像 Apple" | Apple 至少对应玻璃、极简、材料三张卡 | "你指的是浮起来的玻璃层，还是干净的大留白？" |
| "科技感" | 赛博朋克与 Dark Tech 都叫科技感，但一个荧光一个克制 | "要荧光蓝紫的赛博，还是近黑 + 单点高光的仪器感？" |
| "年轻一点" | 可能指圆角、可能指撞色、可能指像素 | "年轻是从形状来还是从颜色来？" |

## 三、回显与确认

抽完七维后**立刻渲染一版**再回显（自定义风格仍然生成页面）。顺序不能反：先看再改，比先改再看有效率得多。

回显表格式与 Phase 2 一致：

| 维度 | 我从描述里读到的 | 取值 | 依据（哪句话） |
|---|---|---|---|
| 中性色温度 | 冷、带一点蓝 | `H 250, C 0.004` | "像实验室的台面" |
| 彩度上限 | 极克制 | `C ≤ 0.07`，彩色 1 处 | "不要花" |
| 圆角 | 几乎没有 | `2 / 4 / 6 / 999` | "利落" |
| 边框 | 极细，承担结构 | `1px`，`fg 8%` | "像图纸" |
| 阴影 | 只给浮层 | `--shadow-3` 单独一档 | `null`（规则默认） |
| 字重 | 中等偏轻 | `400 / 500 / 600` | "安静" |
| 动效 | 快 | `100–140ms`，`ease-out` | `null` |

写完后必须做三件事：

1. 标出**与最接近那张卡的差异**（"和极简的差别是：底色更冷、圆角更小、没有强调色"）；
2. 标出**没有依据的维度**（`from: null`），说明取的是哪个规则默认；
3. 问一句"要不要存成可复用的卡"——默认不存。

---

## 四、什么情况下应该新建卡

同时满足下面三条才建：

1. **结构级差异**：至少一个签名特征是结构级的（栅格、形状系统、层叠语义），而不是配色或字体。
2. **七维里 ≥ 3 维在所有现有卡区间之外**。举例：`H 30 / C 0.04`（暖褐）、`--r-* 全 0`、硬偏移阴影——这三条同时出现时，最接近的卡会是粗野主义，但它不暖也不褐，此时新建是合理的。
3. **anti 列表不与现有卡冲突**。如果新卡的 anti 说"不要硬阴影"，而它其余特征又很像粗野主义，那它就是"粗野主义 - 硬阴影"，是变体不是新卡。

### 新建卡的完整代价

新增一张卡会打破"10 卡 / 12 变体"的口径，而这句话写在 `SKILL.md` §2 与 Studio 的计数里。所以必须一次做完：

```
1. references/styles/<id>.md          ← 按 _schema.md 八段写
2. references/styles/style-index.json ← cards +1，variants +1
3. assets/studio/styles/<id>.css      ← 变体 CSS（另一批产物）
4. SKILL.md §3 Phase 1 候选判据        ← 补一行"什么场景推荐它"
```

缺任何一步，`style-index.json` 与磁盘不一致，批次 6 的验收项（"条目数与 `*.css` 文件数一致"）直接失败。

**不做完这五步的"新卡"只是一次性转写**，以 `decisions.json.direction` 里的 `custom` 记录存在，不进 index、不进画廊、不参与候选推荐。

## 五、为什么默认不新建

| 代价 | 具体表现 |
|---|---|
| 计数口径被打破 | 三处文档 + 一处 JSON + 一个 CSS 文件必须同步，漏一处就出现"10 还是 11"的老问题 |
| 维护成本是平方级 | 每加一张卡，与其余 10 张的交叉比较（anti 是否冲突、候选判据是否重叠）都要重做 |
| 转写质量下降 | 卡的签名特征需要实测校准（ΔL、对比度、性能），一次性的自定义描述没有这个校准过程 |
| 用户其实想要的是覆盖 | 经验上 80% 的"我想要一个新风格"用"已有卡 + 换配色 + 改两个圆角"就满足了 |

**反面判据**：如果用户描述里的 anti 列表几乎就是某张卡的签名特征（"不要圆角、不要模糊、不要渐变" ≈ 新粗野主义），那他不是要新风格，是要更极端的已有风格。

## 六、记录格式

自定义风格不写新文件，写进 `decisions.json`：

```json
{
  "direction": {
    "director": "self",
    "custom": {
      "sourceText": "用户原话，逐字保留",
      "baseCard": "minimalism",
      "deviations": [
        { "dim": "neutralTemp", "value": "H 250, C 0.004", "from": "像实验室的台面" },
        { "dim": "radius", "value": [2, 4, 6, 999], "from": "利落" }
      ],
      "promotedToCard": false
    }
  }
}
```

- `baseCard` 必填。即使七维全部偏离，也要写明"最近的那张卡是谁"，作为日后维护的锚点。
- `sourceText` 逐字保留。**不要改写用户原话**——日后审计时它是唯一能核对 `from` 的依据。
- `promotedToCard` 默认 `false`；变成 `true` 的那天，必须已经走完第四节的五步。
