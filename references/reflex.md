# REFLEX · 模型的默认手

> 什么时候读这份：每次准备说「先这样做」的时候。Phase 2 转写前过一遍，Phase 6 出报告前再对一遍。

---

## 为什么单列一层

MUST / SHOULD / ADVISORY 按**强度**分：它们回答「这样做是不是错的」。
REFLEX 按**来源**分：它回答「这是不是模型想都没想就会做的默认手」。

一句话区别——**MUST 是「这样做是错的」，REFLEX 是「这样做是模型的默认手：看起来合理，但通常没经过判断」**。

默认手不等于违规。它是模型在缺少信息、缺少确认、缺少业务上下文时的第一反应：多做一套显得周到，先给全套控件显得专业，把动作做完就显得负责。问题不在于它难看，而在于**它替用户做了一个用户没参与的决定**。

所以在 `references/rules/00-non-negotiable.md` 的优先级链里，REFLEX 就是最底层的「模型默认」；它上面依次是用户显式要求、MUST、导演层方向、SHOULD、检测器默认规则。命中 REFLEX 时只要求两件事：

1. **做之前，分清这是判断还是惯性。**
2. **不做，要给理由，并登记到 `alignment-report.md` 的 Reflex 区。**

登记一行就够：

```
X1 · 不做 · 理由：brief 明确「本期不做暗色」 · 确认人：user · 时间：2026-11-03
```

登记区不是惩罚记录，是**下一次会话能读到的判断依据**。

## 总表

| # | 默认手 | 为什么它看起来合理 | 什么时候可以不做 | 怎么留痕 |
|---|---|---|---|---|
| X1 | 替用户做决定 | 多做一套显得周到、留了余地 | brief / 导演层已明确要哪一套，或纯技术必需 | 意图状态位 + 写进 brief |
| X2 | 把发出当收到 | 动作已经完成，流程看起来在推进 | 对方是脚本 / 无人值守队列，不存在「确认」 | 回执字段（`confirmedBy` / `confirmedAt`） |
| X3 | 不知道就编 | 给出选项比反问更像「在帮忙」 | 标明是提案、给出依据、允许否决 | 提案与事实分栏，事实必须有 `sourceQuote` |
| X4 | 专家控件摆在主路径 | 能力齐全显得专业，用户想深入时不用找 | 用户明确要全量参数，或本身就是专家工具 | 默认路径写进 brief + 首屏决策点预算 |

## 逐条展开

### X1 · 替用户做决定

- **表现**：brief 没提的事，默认按「更完整」补齐——两套主题、两个模式、两套文案。用户没反对，就当成同意。
- **真实例子**：Studio 没问就写出 `light-dark` 两套 token，而用户 brief 写明「本期不做暗色」。多出来的一套不是礼物，是没人认领的维护成本。
- **可机器查**：`decisions.json.meta.theme` 与 brief 原文比对；brief 没有「暗色 / dark / 深色」而 `meta.theme === 'light-dark'` 即命中。
- **什么时候可以不做**：brief、导演层产物或 schema 已明确写了要哪一套；或者这是纯技术必需（如 `forced-colors` 的系统行为），不是设计选择。
- **怎么留痕**：**意图状态位 + 写进 brief**。`decisions.json.meta` 记 `theme.intent`（`light` / `light-dark`）与 `source`（`brief` / `director` / `user`），brief 回显里出现同一句。

### X2 · 把发出当收到

- **表现**：把「我做了动作」当成「对方收到了」：URL 写进日志、消息写进文件、报告发出去，就继续往下走。
- **真实例子**：Studio 启动后只在终端打印 `Studio <url>`，没在对话里给可点击链接，也没等用户说「打开了」就开问 Phase 0。
- **可机器查**：工作台交接记录里有没有 `confirmedBy` / `confirmedAt`；报告机读区有没有回执字段；没有回执就判未完成（需人工核对对话）。
- **什么时候可以不做**：对方是脚本或无人值守队列（CI 产物、定时任务），不存在「确认」这个概念——但仍要留下产物路径与时间。
- **怎么留痕**：**回执字段**：`handoff: { channel, deliveredAt, confirmedBy, confirmedAt }`。没有 `confirmedBy` 就不算交接完成。

### X3 · 不知道就编

- **表现**：不知道业务对象，就自拟几个页面选项让用户三选一；不知道依据，就把自己的推断写成「来自你的描述」。
- **真实例子**：Phase 0 还没搞清系统管什么，就编出「仪表盘 / 列表 / 详情」三个候选页，用户只能在 agent 虚构的选项里选。
- **可机器查**：brief 里每个业务名词能否指回用户原话；`translation.from` 为 `null` 却填了引用；候选页面是否出现在用户消息里。
- **什么时候可以不做**：这是**提案**而不是**事实**，并且明确标注为提案、给出依据、允许用户否决——提案本身是允许的，冒充事实不行。
- **怎么留痕**：**提案与事实分栏**。提案写 `proposal: true` + 依据；事实必须有 `sourceQuote`。没有依据就老实写 `from: null`，那不是缺陷，是信息。

### X4 · 专家控件摆在主路径

- **表现**：把「完整能力」放在第一屏：先给色相环而不是预设方案，先给全部命令而不是 3 个推荐，先给七维全开而不是逐项引导。
- **真实例子**：调色页把色相环摆在最前面，默认用户想从零调色；用户其实只想在 3 个候选里选一个，再微调两下。
- **可机器查**：首屏可交互控件数量、默认展开的专家面板数、主任务需要几步；「预设 / 推荐」入口是否排在自定义入口之前。
- **什么时候可以不做**：用户明确说「我要自己调」「给我全部参数」；或者这本来就是专家工具，用户就是设计师。
- **怎么留痕**：**默认路径写进 brief**：`defaultPath: preset | advanced`，并约定首屏决策点预算（建议 ≤3）。超预算要么折叠，要么在报告里写明为什么这一屏需要这么多。

### X5 · 静默失败

- **表现**：格式写错不报错、非法值悄悄回退默认、控件改了但没接写回；用户以为改了，实际没改。
- **真实例子**：调色面板的 hex 输入非法时直接回退到上一个颜色，没有提示；用户以为新颜色已经保存，直到下一屏才发现没变。
- **可机器查**：写回端点的 4xx/5xx、控制台错误、`decisions.json` 的修改时间与 UI 操作时间是否对得上；非法输入有没有可见错误文案。
- **什么时候可以不做**：失败是**预期内**且已明确告知（例如浏览器不支持某特性，走降级链并在界面上显示降级状态）。
- **怎么留痕**：**失败要出声**：UI 显示错误、脚本用非零退出码、无法自动验证时写 `manual-required`。禁止「回退到默认值并当作成功」。

### X6 · 只改一半链路

- **表现**：改了 token 没接预览、改了控件没接序列化、加了状态没接渲染；每一步单看都对，连起来是断的。
- **真实例子**：新增 `--radius-card` 只写进 `tokens.css`，没有重跑 `build.mjs`，合同和注入块仍是旧值，G3 的 `sourceHash` 对不上。
- **可机器查**：`check-consistency.mjs` 的 `sourceHash`；UI 控件 → `decisions.json` → `tokens.*` → `contract.md` 的端到端用例；schema 校验。
- **什么时候可以不做**：链路本身只有一段（例如纯文档措辞修改），确实没有派生或消费方。
- **怎么留痕**：**一条链一次改完**：列出「源 → 派生 → 消费方」三段逐段打勾，并贴 `check-consistency` 输出。只改源不跑生成，不算改完。

### X7 · 用默认模板冒充设计

- **表现**：居中等宽卡片、标题上方小标签、紫蓝渐变、Inter；每一处都「不难看」，合起来是任何产品都能套的模板。
- **真实例子**：不问品牌气质，直接产出「标题 + 副标题 + 三张等宽卡片 + 紫蓝渐变按钮」的落地页，换个 logo 就能给下一家。
- **可机器查**：`audit.mjs` 可查字体族、渐变、卡片布局；grep `Inter` / `linear-gradient` / 居中等宽卡片；与 `references/styles/*.md` 的签名特征比对。
- **什么时候可以不做**：品牌本身就用这套语言（例如企业内部系统明确要求跟现有设计系统一致），且这是经过确认的约束，不是偷懒。
- **怎么留痕**：**签名特征清单**：`contract.md` 第 1 段写这个方向「一眼能认出的 3 个特征」，Phase 6 的 L3 逐条对照。

### X8 · 把检查清单当结果

- **表现**：报告写「全部满足」，但没有命令输出、没有截图、没有 hash；用口头结论代替证据。
- **真实例子**：`alignment-report.md` 的 L1 / L2 表格全打勾，但粘贴的输出是手写的，`checkedAt` 与脚本实际运行时间对不上。
- **可机器查**：每个 `✓` 是否紧跟真实命令输出块；`toolVersions`、`checkedAt`、`sourceHash` 是否与产物一致；截图路径是否真实存在。
- **什么时候可以不做**：检查项确实无法自动化（例如纯主观的 L3），此时必须写 `manual-required` 和人工结论，不能写「通过」。
- **怎么留痕**：**附证据**：命令输出或截图路径，不接受口头通过；截图必须能在 `shots/` 找到对应文件。

### X9 · 一次给太多

- **表现**：七个维度同时可编辑、五个下拉、24 个命令；把「能力齐全」当成「好用」。
- **真实例子**：转写面板一屏放出七维控件，用户不知道先改哪个，最后全部接受默认值——面板等于没起作用。
- **可机器查**：首屏决策点数量、默认展开的表单字段数、完成一次主任务是否需要滚动；主任务步数。
- **什么时候可以不做**：用户是专家且明确要求全量界面；或者这是「全部设置」页，主路径在别处。
- **怎么留痕**：**预算写进 brief**：一次最多 3 个决策点；超出就分步或折叠，并在报告里登记「为什么这一屏需要 N 个」。

## 怎么用这一层

| 时机 | 动作 |
|---|---|
| Phase 0 写 brief | 过 X1 / X3：哪些是用户说的，哪些是我补的；补的写进提案栏 |
| Phase 2 转写 | 过 X4 / X9：默认路径是哪条，首屏给几个决策点 |
| Phase 5 落地 | 过 X5 / X6：失败有没有出声，链路有没有跑通到消费方 |
| Phase 6 出报告前 | 过 X2 / X7 / X8：交接有没有回执，设计有没有签名，结论有没有证据 |

**不用为每条都写一段。** 只有「决定不做」时才登记；做了且理由清楚的，不占篇幅。
