# 对用户怎么说话

内部术语是给维护者、脚本和日志看的：它精确、短、可检索。但对第一次用这个 skill 的用户，`转写`、`依据`、`G2`、`ΔL` 这些词等于黑话——用户不知道自己被问的是什么，也就无法确认。同一个概念准备两套说法：**内部用术语保证精确，对用户用白话保证可懂。** 这份表就是两套说法之间的对照。

---

## 对照表

| 内部术语 | 什么时候会出现 | 对用户怎么说 |
|---|---|---|
| `转写` | Phase 2 开头，把风格描述变成数值 | 「我接下来把你描述的风格翻成具体数字——比如灰底偏冷还是偏暖、圆角几像素、用不用阴影。这样写代码时不用猜，做完也能一项项核对。」 |
| `转写表` | G2 回显、写进合同第 2 段 | 「这张表把你说的风格翻成了七个具体数值，每一行都注明我是从你哪句话推出来的；你可以逐行改。」 |
| `依据` | 转写表的最后一列 | 「表里最后一列写的是：这一条是从你哪句话推出来的。你没提过的，我会写『按常规默认』，不假装是你说的。」 |
| `七维` / `七个维度` | 解释转写表覆盖什么 | 「这张表一共管七件事：灰的冷暖、颜色最多能有多艳、圆角多大、有没有边框、阴影多重、字多粗、动画多快。」 |
| `G0` | Phase 0 末，确认做什么、给谁用、先做哪页 | 「先一起定三件事：这个系统主要管什么、给谁用、先做哪个页面；定完我们再谈风格。」 |
| `G1` | Phase 1 末，确认风格方向 | 「风格方向定下来了，你确认后我就把它变成具体数值。」 |
| `G2` | Phase 2 中，确认数值表 | 「数值表填好了，你逐行确认后我才开始排页面。」 |
| `G3` | Phase 4 末，合同自检 | 「设计文件生成完了，我先自查一遍前后有没有对不上的地方。」 |
| `G4` | Phase 6 末，视觉对齐 | 「实现做完了，我把截图和当初确认的样稿逐页对照；全部对上才算完成。」 |
| `闸门` | 说明流程进度 | 「这是流程里的一道确认关口：过了才往下走，没过就退回去改。」 |

| `OKLCH` | 色值、调色面板、对比度计算 | 「你会在色值里看到 `oklch(...)` 这样的写法。它和十六进制一样是描述颜色，但把明暗、鲜艳程度和色相分开写，调明暗时不会顺带改到色相。」 |
| `导演层` | 说明谁定风格 | 「风格和气质由谁说了算——可能是另一个设计工具，也可能是我内置的风格库。」 |

| `验收层` | 说明本 skill 的职责 | 「我在这件事里的另一个角色，是做完之后拿实际页面和当初确认的样稿逐页对照。」 |

| `L3` | Phase 6 第三层检查 | 「这一项靠眼睛：把做出来的页面和当初确认的样稿并排看，找肉眼能看出的偏差。」 |

| `provenance 头` | 生成文件开头 | 「文件开头会有一段生成记录，说明它从哪份决策生成、什么时候生成、用的哪个版本。」 |

## 什么时候可以保留术语

以下三种情况照原样说，甚至应该保留：

- **用户自己先用了这个词。** 跟着用户说，不要反过来纠正他。
- **它是文件里的标识符、命令、字段名或规则编号，且用户正在看那个文件或终端。** 例如 `decisions.json`、`check-tokens.mjs`、`R4`：保留原文，但同一句里补一句白话。
- **用户明确问「这个字段叫什么」「这个编号是什么」。** 这时术语就是答案，可以给，并说明它管什么。

以下三种情况**必须**换成右列白话：

- **第一次出现。** 不管用户看起来懂不懂。
- **解释流程、进度、下一步做什么。**
- **请求用户确认或做选择。** 包括闸门、验收结论、是否接受例外。

拿不准时用「白话（术语）」格式，例如：把你描述的风格翻成具体数字（内部叫「转写」）。一句话里最多出现一个术语；用户没主动用过的词，不要连着抛两个。

## 反例

原句：

> 请确认七维转写表与 G2 依据。

这句话连抛三个内部词，用户不知道要确认什么。改成：

> 这张表把你说的风格翻成了七个具体数值：灰的冷暖、颜色多艳、圆角多大、边框、阴影、字重、动画快慢。每一行都注明了我是从你哪句话推出来的；你没提过的会标「按常规默认」。你看一遍，哪行不对直接说，我改完再往下做。

聊天里只够说一句时的短版：

> 我把你的风格描述翻成了七个具体数值，每项都注明是从你哪句话来的，你逐行确认一下。
